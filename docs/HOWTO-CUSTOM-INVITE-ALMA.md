# How-to: serve the custom Ward invite page on AlmaLinux

This runbook replaces Prosody's built-in invite page with the custom Ward landing
page shipped in `proctor/data/invite/index.html`. It is written for a host that
was already set up by Proctor, uses nginx, and keeps its Prosody community
modules in `/opt/prosody-modules`.

The example domain is `example.com`. Replace it with the real XMPP/web domain.

This procedure does **not** reinstall Proctor or Prosody and does not modify user
accounts, rosters, uploads or passwords. It changes only:

- Prosody's `plugin_paths`, enabled modules and invite-page settings;
- the static invite page at `/usr/local/share/proctor/invite/index.html`;
- the nginx vhost generated by Proctor.

> **Do not run `proctor setup` just to apply this guide.** Setup regenerates the
> Prosody and nginx configuration and reinstalls the page template. The last
> section explains how to make the change survive a future setup run.

## 0. What the pieces are

| Piece | Purpose |
|---|---|
| `mod_invites` | Creates and consumes invite tokens |
| `mod_invites_page` | Generates invite URLs and supports an external page |
| `mod_invites_register_web` | Handles the `/register` form POST |
| `mod_register_apps` | Supplies the XMPP client/app list used by Prosody's stock pages |
| `mod_password_policy` | Optional password rules during registration |
| `/usr/local/share/proctor/invite/index.html` | The custom Ward page |
| nginx `location = /ward-invite` | Serves that static page |
| nginx `location ^~ /register` | Proxies registration to Prosody |

Request flow:

```text
https://example.com/ward-invite?TOKEN
        |
        v
nginx location = /ward-invite
        |
        v
/usr/local/share/proctor/invite/index.html
        |
        | form POST /register
        v
nginx location ^~ /register  ->  Prosody 127.0.0.1:5280
        |
        v
mod_invites_register_web
```

The page is self-contained: CSS, SVG and JavaScript are inline. It does not need
Prosody to render it, and it does not need an extra web root besides the one
static file.

## 1. Preflight and backup

```sh
sudo proctor doctor
sudo proctor discover
sudo prosodyctl about
sudo prosodyctl check
```

`proctor discover` shows the actual Prosody config path, data path and plugin
directories. Use those values below.

Set shell variables for the common paths:

```sh
PROSODY_CFG=/etc/prosody/prosody.cfg.lua
NGINX_CFG=/etc/nginx/conf.d/proctor-xmpp.conf
```

If Prosody is installed under `/opt`, the config is often:

```sh
PROSODY_CFG=/opt/prosody/etc/prosody/prosody.cfg.lua
```

If `prosodyctl` is not on `PATH` for a source install under `/opt`, use the
absolute path:

```sh
sudo /opt/prosody/bin/prosodyctl about
sudo /opt/prosody/bin/prosodyctl check
```

Tell Proctor about the Alma module tree as well, so `doctor`, `discover` and
backups include it. Merge this into `/etc/proctor/config.json` without removing
the existing keys:

```json
{
  "prosody": {
    "config": "/opt/prosody/etc/prosody/prosody.cfg.lua",
    "data_dir": "/opt/prosody/var/lib/prosody",
    "log_dir": "/opt/prosody/var/log/prosody",
    "plugin_dirs": ["/opt/prosody-modules"]
  }
}
```

Then re-run:

```sh
sudo proctor doctor
sudo proctor discover
```

This makes Proctor's `plugins` backup include `/opt/prosody-modules`. It does
not by itself change the generated Prosody config; the `plugin_paths` edit below
is still required.

Take a verified backup and copy the two files you are about to edit:

```sh
sudo proctor backup --verify --tag before-custom-invite

sudo cp -a "$PROSODY_CFG" \
  "$PROSODY_CFG.bak.$(date +%F-%H%M)"

sudo cp -a "$NGINX_CFG" \
  "$NGINX_CFG.bak.$(date +%F-%H%M)"
```

If `$NGINX_CFG` does not exist, find the active vhost first:

```sh
sudo nginx -T | grep -n 'server_name\|ward-invite\|proctor-xmpp'
```

## 2. Confirm the modules exist in `/opt/prosody-modules`

```sh
ls -ld /opt/prosody-modules

for m in invites invites_page invites_register invites_register_web register_apps password_policy; do
    if [ -e "/opt/prosody-modules/mod_$m.lua" ] ||
       [ -d "/opt/prosody-modules/mod_$m" ]; then
        echo "ok      $m"
    else
        echo "MISSING $m"
    fi
done
```

Prosody accepts either a single-file module:

```text
/opt/prosody-modules/mod_invites_page.lua
```

or a multi-file module directory:

```text
/opt/prosody-modules/mod_invites_page/mod_invites_page.lua
```

The exact required modules for this page are:

```text
invites
invites_page
invites_register_web
```

`register_apps` and `password_policy` are recommended but the custom page does
not depend on Prosody's built-in app list or styling.

### If a module is missing

Clone the community modules once, then link the missing module directories into
`/opt/prosody-modules`:

```sh
sudo dnf install mercurial

if [ ! -d /usr/local/lib/prosody-modules/.hg ]; then
    sudo hg clone https://hg.prosody.im/prosody-modules/ \
        /usr/local/lib/prosody-modules
else
    sudo hg -R /usr/local/lib/prosody-modules pull --update
fi

for m in invites invites_page invites_register invites_register_web register_apps password_policy; do
    src="/usr/local/lib/prosody-modules/mod_$m"
    dst="/opt/prosody-modules/mod_$m"
    if [ -e "$src" ] && [ ! -e "$dst" ]; then
        sudo ln -s "$src" "$dst"
    fi
done
```

Some of these modules are shipped inside Prosody itself, especially `invites`
and `invites_register` on newer installations. A `MISSING` line does not matter
if Prosody already provides the module; `prosodyctl check` will confirm that.

## 3. Add `/opt/prosody-modules` to `plugin_paths`

Proctor's generated Prosody config normally contains:

```lua
plugin_paths = { "/usr/local/lib/prosody-modules-enabled" }
```

On this host, extend it to include the Alma module tree. Keep Proctor's enabled
directory too, because Proctor may have cloned a missing module there.

Open the config:

```sh
sudoedit "$PROSODY_CFG"
```

Replace the `plugin_paths` line with:

```lua
plugin_paths = {
    "/opt/prosody-modules";
    "/usr/local/lib/prosody-modules-enabled";
}
```

The order matters. Put the directory whose module versions you trust first.

If the file has no `plugin_paths` line, add the block near the top, before
`modules_enabled`.

## 4. Enable the invite modules and point them at the page

In `modules_enabled`, keep all existing entries and add any of these that are not
already present:

```lua
modules_enabled = {
    -- existing modules...
    "invites";
    "invites_page";
    "invites_register";
    "invites_register_web";
    "register_apps";
    "password_policy";
}
```

Then add or verify these settings. They normally live near
`allow_registration`, `http_external_url` or `http_ports`:

```lua
allow_registration = false

http_external_url = "https://example.com"

invites_page_external = true
invites_page = "https://example.com/ward-invite?{invite.token}"
site_name = "example.com"
```

`invites_page_external = true` is the important switch. It tells
`mod_invites_page` not to render Prosody's built-in page and to use the external
URL instead. `{invite.token}` is substituted by Prosody when an invite is
created.

Leave `allow_registration = false`. Invite-based registration does not need open
registration.

Validate and restart:

```sh
sudo prosodyctl check
sudo systemctl restart prosody
sudo systemctl status prosody --no-pager
```

If `prosodyctl check` reports a missing module, fix `plugin_paths` or install the
module before continuing. Check the log if it starts but invite URLs still use
the built-in page:

```sh
sudo journalctl -u prosody -n 100 --no-pager
```

## 5. Install the custom page

The page is in the Proctor source tree at:

```text
proctor/data/invite/index.html
```

From the repository root, install it as root and make it readable by nginx:

```sh
sudo install -D -m 0644 \
    proctor/data/invite/index.html \
    /usr/local/share/proctor/invite/index.html

sudo chown root:root /usr/local/share/proctor/invite/index.html
sudo chmod 0755 /usr/local/share/proctor /usr/local/share/proctor/invite
```

If the Proctor checkout is not on the target host, copy it from the machine that
has it:

```sh
scp proctor/data/invite/index.html root@target-host:/tmp/ward-invite.html

ssh root@target-host '
    install -D -m 0644 /tmp/ward-invite.html \
        /usr/local/share/proctor/invite/index.html
    chown root:root /usr/local/share/proctor/invite/index.html
    chmod 0755 /usr/local/share/proctor /usr/local/share/proctor/invite
'
```

Do **not** copy the standalone homepage HTML here. That is the homepage, not the
invite page. The invite page is the one at `proctor/data/invite/index.html`.

If SELinux is enabled, label the directory now:

```sh
sudo restorecon -Rv /usr/local/share/proctor/invite
```

## 6. Add the nginx locations

Edit the Proctor-generated vhost:

```sh
sudoedit "$NGINX_CFG"
```

Keep all existing Proctor proxy locations. Add this exact-match location for the
page:

```nginx
location = /ward-invite {
    root /usr/local/share/proctor/invite;
    try_files /index.html =404;
    default_type text/html;
}
```

Confirm that `/register` is proxied to Prosody. If the block is missing, add it:

```nginx
location ^~ /register {
    proxy_pass http://127.0.0.1:5280;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_http_version 1.1;
    proxy_read_timeout 3600s;
}
```

`location = /ward-invite` is an exact match, so it wins over `location /`
regardless of where it appears. The `location ^~ /register` prefix takes
precedence over a generic static fallback.

If the same vhost also serves the homepage from `/var/www/html`, keep the
homepage fallback separate:

```nginx
root /var/www/html;
index index.html;

location / {
    try_files $uri $uri/ =404;
}
```

The invite page location above still wins for `/ward-invite`, and the Proctor
proxy locations still win for `/register`, `/http-bind`, `/xmpp-websocket`,
`/upload`, `/invites_page` and `/.well-known/host-meta`.

Test and reload:

```sh
sudo nginx -t
sudo systemctl reload nginx
```

Confirm the active config contains the new location:

```sh
sudo nginx -T | grep -n -A4 'ward-invite'
```

## 7. SELinux on AlmaLinux

If the page loads but nginx returns 403, the file label is wrong:

```sh
sudo ls -Z /usr/local/share/proctor/invite/index.html
```

The type should be `httpd_sys_content_t`. Fix it with:

```sh
sudo restorecon -Rv /usr/local/share/proctor/invite
```

If `restorecon` does not correct it, add a persistent rule:

```sh
sudo dnf install policycoreutils-python-utils
sudo semanage fcontext -a -t httpd_sys_content_t \
    '/usr/local/share/proctor/invite(/.*)?'
sudo restorecon -Rv /usr/local/share/proctor/invite
```

If nginx returns 502 for `/register`, check whether SELinux is blocking the
proxy:

```sh
sudo setsebool -P httpd_can_network_connect 1
sudo ausearch -m avc -ts recent
```

The simplest alternative on a stubborn SELinux host is to put the page under the
already-labeled web root:

```text
/var/www/html/ward-invite/index.html
```

and serve it with:

```nginx
location = /ward-invite {
    root /var/www/html;
    try_files /ward-invite/index.html =404;
    default_type text/html;
}
```

Either layout works. Proctor's default installer uses
`/usr/local/share/proctor/invite`.

## 8. Test the whole flow

First confirm the static page:

```sh
curl -I https://example.com/ward-invite
curl -s https://example.com/ward-invite | grep -F 'Create my account'
```

A request without a token should still return the styled page and tell the user
the link is missing its token.

Generate a fresh invite:

```sh
sudo prosodyctl mod_invites generate example.com
```

Open the URL it prints. It should look like:

```text
https://example.com/ward-invite?TOKEN
```

Then:

1. Open it in a private browser window.
2. Choose a username and password.
3. Submit the form.
4. Confirm the success screen shows the JID and password.
5. Log in with Ward or another XMPP client.
6. Try the same invite again; it should be rejected as already used.

Watch the server side while testing:

```sh
sudo journalctl -u prosody -f
sudo journalctl -u nginx -f
```

Expected behavior:

- A valid token shows the registration form.
- An invalid or used token shows an error after submission.
- `/register` returns Prosody's success page to the fetch request, and the page
  converts it to the styled success card.
- Keep `allow_registration = false`; invite registration still works through
  the one-time token.

## 9. Make it survive `proctor setup`

`proctor setup` is a provisioning command, not an upgrade command. It rewrites:

```text
$PROSODY_CFG
$NGINX_CFG
/usr/local/share/proctor/invite/index.html
```

That means a later setup run will:

- replace `plugin_paths` with only
  `/usr/local/lib/prosody-modules-enabled`;
- regenerate the nginx vhost from Proctor's template;
- reinstall the page from the Proctor package template.

The page template itself is the same flashy page, so reinstalling it is harmless
if you have not edited the installed copy directly. The module path is the part
that needs attention.

### Option A: Reapply the `/opt` module path after setup

Run setup, then edit `$PROSODY_CFG` again and restore:

```lua
plugin_paths = {
    "/opt/prosody-modules";
    "/usr/local/lib/prosody-modules-enabled";
}
```

Restart Prosody and recheck:

```sh
sudo prosodyctl check
sudo systemctl restart prosody
```

Also reapply any custom homepage `location /` block to the regenerated nginx
vhost.

### Option B: Make Proctor's default path resolve to `/opt`

If `/opt/prosody-modules` is the canonical module tree and the existing
`/usr/local/lib/prosody-modules-enabled` has nothing unique, point Proctor's
expected path at `/opt`:

```sh
# Inspect first.
ls -ld /usr/local/lib/prosody-modules-enabled
ls -l /usr/local/lib/prosody-modules-enabled 2>/dev/null

# If it is a real directory, merge anything unique into /opt before replacing it.
# Preserve the old directory as a backup.
if [ -d /usr/local/lib/prosody-modules-enabled ] &&
   [ ! -L /usr/local/lib/prosody-modules-enabled ]; then
    sudo cp -an /usr/local/lib/prosody-modules-enabled/. /opt/prosody-modules/
    sudo mv /usr/local/lib/prosody-modules-enabled \
        /usr/local/lib/prosody-modules-enabled.pre-opt
fi

sudo ln -sfn /opt/prosody-modules /usr/local/lib/prosody-modules-enabled
```

Now Proctor's generated line:

```lua
plugin_paths = { "/usr/local/lib/prosody-modules-enabled" }
```

resolves to `/opt/prosody-modules`, and setup no longer drops the Alma module
tree. If a module is still missing, Proctor's `ensure_community_modules` clones
it into `/usr/local/lib/prosody-modules` and links it into the enabled path.

Do not use this option if `/opt/prosody-modules` is a package-managed directory
that you do not want Proctor to write symlinks into.

### Option C: Keep the custom HTML in the package

For a permanent page change, edit the source template in the Proctor checkout:

```text
proctor/data/invite/index.html
```

Then reinstall or rerun setup. Editing only
`/usr/local/share/proctor/invite/index.html` is fine for a quick fix, but setup
will overwrite it from the package template.

## 10. Rollback

Restore the saved files and restart:

```sh
sudo cp -a "$PROSODY_CFG.bak.YYYY-MM-DD-HHMM" "$PROSODY_CFG"
sudo cp -a "$NGINX_CFG.bak.YYYY-MM-DD-HHMM" "$NGINX_CFG"

sudo prosodyctl check
sudo systemctl restart prosody
sudo nginx -t
sudo systemctl reload nginx
```

If you used the symlink option, restore the old enabled path:

```sh
sudo rm /usr/local/lib/prosody-modules-enabled
sudo mv /usr/local/lib/prosody-modules-enabled.pre-opt \
    /usr/local/lib/prosody-modules-enabled
sudo systemctl restart prosody
```

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `404` on `/ward-invite` | nginx location missing or wrong `root` | Add `location = /ward-invite`; run `nginx -T` |
| `403` on `/ward-invite` | SELinux label | `restorecon -Rv /usr/local/share/proctor/invite` |
| `502` on `/register` | Prosody down or SELinux proxy denial | Check `systemctl status prosody`; `httpd_can_network_connect` |
| `module 'invites_page' not found` | `plugin_paths` does not include the module tree | Add `/opt/prosody-modules`; restart Prosody |
| Page shows "missing its token" | URL was opened without the token | Generate a new invite |
| Form says account could not be created | Token invalid/used, username taken, or password policy | Check `journalctl -u prosody`; generate a fresh invite |
| Invite URL still points at `/invites_page` | `invites_page_external` or `invites_page` not active | Fix config; restart Prosody |
| Page is unstyled | Wrong HTML file copied | Reinstall `proctor/data/invite/index.html` |
| Registration succeeds but no success card | `/register` response changed | Check the fetch response in browser dev tools and Prosody logs |
| `prosodyctl check` warns about a module | Module not present in `/opt` or enabled path | Install/link it or remove it from `modules_enabled` |

Useful commands:

```sh
sudo prosodyctl check
sudo prosodyctl about
sudo systemctl status prosody nginx --no-pager
sudo nginx -T | grep -n -A4 'ward-invite'
sudo journalctl -u prosody -n 100 --no-pager
sudo journalctl -u nginx -n 100 --no-pager
sudo proctor doctor
```
